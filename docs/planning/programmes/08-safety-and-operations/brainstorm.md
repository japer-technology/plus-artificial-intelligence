# Brainstorm — Programme 08: Safety and Operations

> Companion to [`08-safety-and-operations.md`](../08-safety-and-operations.md). Every member suggestion is decomposed here into **definitive features** and **pre-implementation decisions**; each has one agent request in [`requests/`](requests/). Workflow: open a request, record your choices in its §1, then give the file to your agent.

## Programme-level decisions (affect more than one request)

1. **Hosted-service launch gate (shared mechanism).** Every P3 hosted service (relay, profiles, workspaces, hosting, priority review) ships four Programme-8 artifacts before launch: a static-first **failure-mode statement** (`static-first-service-architecture`), a **threat model** (`security-and-abuse-controls`), a **privacy analysis** (`privacy-and-data-minimisation`), and a **cost-model entry** (`cost-discipline`). No single artifact opens the gate; the launch review checks all four. Each request surfaces its own slice as a §2 instruction and §3 constraint.
2. **Policy-first-then-enforcement sequencing.** P0 ships the three policy templates (static-first layering → privacy-analysis template → cost model); P1 ships moderation rules + the security baseline; P2 ships moderation queue tooling + child-safe materials; P3 ships per-service instantiations (threat models, privacy analyses, failure-mode statements, degraded-mode demos) — one per hosted launch. Policies gate enforcement: no rule is enforced before it is published, and no service ships before its four artifacts exist.
3. **§11 cross-cutting decisions are placed in named requests (joint owners named):** jurisdiction erasure → `privacy-and-data-minimisation` (joint owner: `declaration-lifecycle`, Programme 2); free-quota sizes (read API + email relay) → `cost-discipline` (consumers: `api-scale-and-reliability` P9, `verification-checker` P3, `privacy-preserving-email-relay` P6); default rate-limit numbers (checker + hosted APIs) → `security-and-abuse-controls` (joint owner: `verification-checker` P3; `cost-discipline` + `api-scale-and-reliability` inform the numbers); registry self-service admission threshold + release cadence → `moderation-disputes-and-appeals` owns the rules-publication + human-review side (joint owner: `opt-in-signatory-registry` P4, whose request already carries the numeric threshold + cadence decisions).
4. **Multi-language placement.** The standard is carried by `privacy-and-data-minimisation` (published analyses/notices are T1; R1 English-governs with the caveat that legal notices need their own care), `moderation-disputes-and-appeals` (rules T1, transparency reports T2), `child-safe-education` (classroom materials T2), `static-first-service-architecture` (failure-mode statements + degraded-mode labels), and `cost-discipline` (published cost model + status copy T2; numeric data T0). `security-and-abuse-controls` does **not** carry it — its public outputs (threat models, rate-limit numbers) are technical/operational reference, and numeric limits are T0 (judgement call recorded here).
5. **Output locations.** Policies and templates live in `docs/`; public pages in `site/*.html`; machine-readable records in `site/*.json`; enforcement tooling (when built) in `scripts/*.mjs`; versioned/annual archives in `site/<name>/`. Consistent with IMPLEMENTATION-PLAN §3 and the Programme 1/4 request folders.

## Member-by-member brainstorm

### privacy-and-data-minimisation — Privacy and Data Minimisation
- **Request:** [`requests/privacy-and-data-minimisation.md`](requests/privacy-and-data-minimisation.md)
- **Definitive features:** privacy policy (`docs/privacy-and-data-minimisation.md`) covering collection minimisation, public/private separation, pseudonym support, retention schedules, exit rights (export/redaction/revocation/deletion), and jurisdiction/processor lists; machine-readable per-field privacy-analysis template (spec §5.3 shape); published analyses for the static site (collects nothing) and the no-account builder (local-only); public `site/privacy.html` notice + analysis index; account-settings page requirement (export / redaction-revocation / deletion / analysis view) instantiated per hosted service at P3.
- **Decisions:** D1 — Deletion-cascade window; D2 — Pseudonym abuse carve-out; D3 — Jurisdiction erasure vs tombstone (joint with declaration-lifecycle); D4 — Translation tier of published analyses/notices.
- **Open questions / risks:** the numeric deletion-cascade window and the pseudonym-abuse carve-out are the spec §10 items (D1–D2); the jurisdiction-erasure conflict with the append-only lifecycle is escalated to legal review rather than resolved here (D3). Risk: policy-only — the template must be wired into launch review or it decays into prose (programme-file risk).

### static-first-service-architecture — Static-First Service Architecture
- **Request:** [`requests/static-first-service-architecture.md`](requests/static-first-service-architecture.md)
- **Definitive features:** layering policy (`docs/static-first-service-architecture.md`) — commons → export → service with one-way dependency direction; failure-mode statement template (spec §5.3 shape: `degradesTo`, `export`, `shutdownNotice`); degraded-mode demonstration requirement + minimum evidence bar; export-first wind-down rule; third-party regeneration posture.
- **Decisions:** D1 — Minimum degraded-mode evidence; D2 — Third-party regeneration of the export pipeline.
- **Open questions / risks:** the minimum degraded-mode evidence and third-party regeneration are the spec §10 items (D1–D2). Risk: the layering rule being honoured in prose but not in launch review (programme-file "policy-only safety" risk) — the hosted-service gate (§1 decision 1) is the countermeasure.

### cost-discipline — Cost Discipline
- **Request:** [`requests/cost-discipline.md`](requests/cost-discipline.md)
- **Definitive features:** cost model (`docs/cost-discipline.md` + `site/cost-model.json`) across the eight categories (storage, bandwidth, moderation, mail, support, backup, abuse, shutdown), annual, with estimates → measured fields; per-record cost measurement in aggregate; structural controls (static views + immutable caching, queued checks, optional media, bounded hosted fetches, offline-first); queued-check backlog status requirement; shutdown reserve reporting; no-paywall rule (covenant amendment only).
- **Decisions:** D1 — Free-quota sizes for read API + email relay (joint, consumers named); D2 — Hosted verification fetch-cost budget; D3 — Per-record cost segmentation by record type.
- **Open questions / risks:** the free-quota sizes and the fetch-cost budget are deferred to measurement, not fixed now ("measure before promising", spec §5.1.1) — D1–D2; per-record-type segmentation is gated on aggregate-safe volumes (D3). Risk: publishing limit numbers before measurement would violate the spec's own principle; the model ships with the numbers marked pending.

### moderation-disputes-and-appeals — Moderation, Disputes, and Appeals
- **Request:** [`requests/moderation-disputes-and-appeals.md`](requests/moderation-disputes-and-appeals.md)
- **Definitive features:** admission + prohibited-content rules (versioned, changelog-announced; ≥ six categories) on `docs/moderation-disputes-and-appeals.md` + `site/moderation.html`; the six-status vocabulary (`pending`, `published`, `restricted`, `removed`, `restored`, `disputed`); moderation event record schema (spec §5.3); notice-and-action + evidence handling; appeals by a different reviewer; emergency restriction (`restricted` + mandatory review date); annual transparency report template + archive (`site/transparency/`).
- **Decisions:** D1 — Response-time targets per category; D2 — Reporter-anonymity carve-out; D3 — Registry self-service admission gate (rules-publication + human-review side; joint with opt-in-signatory-registry).
- **Open questions / risks:** response targets are deferred to staffing reality (spec §10; cost-discipline models moderation cost) — D1; reporter anonymity needs a jurisdiction carve-out (D2); the release-cadence decision itself lives in the registry request (D1 there) — moderation owns only the rules-publication + human-review side (D3). Risk: moderation scale (programme-file risk) — the human-review staffing plan must exist before hosted admission opens.

### security-and-abuse-controls — Security and Abuse Controls
- **Request:** [`requests/security-and-abuse-controls.md`](requests/security-and-abuse-controls.md)
- **Definitive features:** security baseline (`docs/security-and-abuse-controls.md`) — auth (second factors, no biometrics), server-side authorization + immediate revocation, output encoding, strict CSP, URL policy, upload limits, SSRF guard, network isolation, anti-scraping via limits only, dependency patching; threat-model template (spec §5.3 shape); incident-response process; canonical CSP + URL policy + rate-limit defaults on `site/security.html`.
- **Decisions:** D1 — Default rate-limit numbers (joint with verification-checker; cost-discipline + api-scale-and-reliability inform); D2 — CSP publishing location.
- **Open questions / risks:** the numeric rate limits are deferred to cost-discipline modelling (spec §10, §5.2.9 "published here once set operationally") — D1; CSP publishing location is D2. Risk: a hosted surface launching before its threat model exists — guarded by the hosted-service gate (§1 decision 1).

### child-safe-education — Child-Safe Education
- **Request:** [`requests/child-safe-education.md`](requests/child-safe-education.md)
- **Definitive features:** `site/education.html` + `site/education/` materials — classroom guidance and teacher/guardian materials teaching reflection, disclosure, responsibility; private school templates with `organisation-only` scope; local-first student flows (offline, local-file save, no upload); specialist review record per release; jurisdiction notes (age thresholds, guardian consent, gaps disclosed); no-account reporting route documented in student-facing materials.
- **Decisions:** D1 — Age-threshold table per jurisdiction; D2 — Guardian-consent record location.
- **Open questions / risks:** the age-threshold table is pending specialist input (spec §10; the spec's own §5.2.1 requires specialist review before release) — D1; guardian-consent record location is D2. Risk: child-safety gap (programme-file risk) — ship only after specialist review, never before. Minor tension: the Order line's "template flows with workspaces P3" is not restated in the programme's Sequencing P3 list; the Order line is followed.
